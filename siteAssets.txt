siteAssets — favicon, icons, OpenGraph card, sitemap and the 88x31 badge wall
              for dreamstation.systems
================================================================================

Source of truth is ~/configNotes/documentServing/rootdomain/, which mirrors
the live docroot /srv/http. Edit in configNotes, then install to /srv/http as
root.

FAVICON
  The mark is U+2042 ASTERISM, matching the separator already used in the nav
  and meta description. It is drawn as line geometry, not as a text glyph:
  U+2042 is missing from most fonts, and a favicon renderer with no glyph for
  it would draw tofu. Only DejaVu, Free*, Noto Sans Mono, IPA and Unifont have
  it on this box.

  Arm length (5 units) and star spacing in the 32-unit viewBox are tuned so the
  three stars stay visually separate at 16px. Tighter spacing merged them into
  a blob. The asterisk template lives in <defs> — a bare <g> would also be
  painted at the origin, which is a real rendering bug, not just a preview one.

  The SVG follows prefers-color-scheme (#111 light / #eee dark). ICO has no way
  to do that, so it is a fixed mid grey (#666) that stays legible against both
  light and dark browser chrome.

  Caveat: ImageMagick's internal SVG renderer (MSVG) ignores stroke-width
  through <use>, so rasterising favicon.svg with `magick` produces hairlines
  and is NOT a valid preview. makeFavicon.py redraws the geometry from
  primitives instead. If favicon.svg's geometry changes, change the constants
  at the top of makeFavicon.py to match — they are duplicated, not shared.

APPLE TOUCH ICON
  Same geometry, but it cannot reuse the favicon's tricks. iOS composites any
  transparency onto black, so a transparent PNG with the dark #111 mark would
  render as a black square. It is therefore drawn opaque, #111 on #ffffff.

  It is redrawn from primitives rather than recoloured from the favicon's
  512px render: that render is antialiased grey on transparency, and flattening
  it onto white leaves grey fringing on every stroke.

  The mark is inset to 84% of the tile. Edge-to-edge looked cramped beside
  other home screen icons. Do NOT round the corners — iOS applies its own mask,
  and pre-rounded art gets clipped twice.

  Only the 180px size is shipped. iOS downscales it cleanly for every smaller
  slot, and the pile of legacy apple-touch-icon-NNxNN.png variants has not been
  needed since iOS 8.

OPENGRAPH
  Tags live in professional/index.html, after <link rel="canonical">.
  og:description is intentionally shorter than the page's meta description.
  twitter:title/description/image are omitted: they fall back to the og:* tags.

  The card is a terminal mock: `finger robin@localhost`, name, tagline, three
  asterism bullets, URL. Monochrome: pure black background, pure white text,
  saved as a grayscale PNG (the greys are text antialiasing only, not palette).
  Rendered with Pango markup at -pointsize 22; at 30 the
  block overflowed 1200px. Font is Noto Sans Mono, one of the few monospace
  faces here with U+2042.

  The stats on the card (pool score, CVE status) are point-in-time and scrapers
  cache images hard. After re-running makeOg.sh, bust the caches via
  Facebook's Sharing Debugger and LinkedIn's Post Inspector, or the old card
  will keep appearing for weeks.

  Filename gotcha: the file is ogimage.png, NOT og.png. makeOg.sh defaulted to
  og.png until 2026-08-27, which would have silently written an orphan and left
  the real card stale. The default now matches. Do not "tidy" the name —
  scrapers cache og:image URLs hard and a rename costs a re-scrape everywhere.

HEAD TAGS  (professional/index.html)
  Deliberately present: author, robots (max-image-preview:large so Google may
  use the full og card in results), theme-color as a light/dark PAIR with media
  attributes, og:locale (en_US — underscore, not the hyphen used by lang=""),
  profile:first_name/last_name/username (og:type is "profile", which defines
  them), twitter:image:alt.

  Deliberately ABSENT: <meta name="color-scheme">. The inline CSS in the same
  <head> already sets html{color-scheme:light dark}, which is equivalent. Do
  not add it back "for completeness" — it is a second source of truth for the
  same setting.

  profile:gender is also omitted: optional, spec only accepts male/female, and
  nothing meaningful consumes it.

SITEMAP
  sitemap.xml lists only canonical, currently-linked pages: /, /professional/,
  /personal/, /personal/blog.html. Discovered via the Sitemap: line in
  robots.txt (a sitemap nothing points at is a sitemap nobody reads).

  Excluded on purpose, and the exclusions matter more than the inclusions:
    /old/*      the authorized phishing-simulation pages and reveal pages.
                These must never be indexed.
    /oldsite/*  superseded by /personal/.
    the unlinked /personal/*.html orphans carried over from oldsite.

  No priority or changefreq elements — Google ignores both. lastmod IS read, so
  update it only on real content changes; a sitemap that claims everything
  changed today gets its lastmod distrusted wholesale.

THE 88x31 WALL
  The button shelf at the foot of /personal/. Ten badges, on eight pages.

  SOURCE OF TRUTH IS webBadges.csv IN THE REPO ROOT — row order is display
  order, and the columns are the source filename, the alt text, and the link
  (empty link = a bare <img>, for the two badges that point nowhere).

    webBadges.csv                     the wall: order, alt text, links
    assetsBuild/badgesSrc/            source images, never served
    assetsBuild/badgeBuild.pl         the builder, run from preCommit.sh
    assetsBuild/badgeManifest.txt     generated: encode cache + audit trail
    rootdomain/personal/badges/       generated: what is actually served

  ADDING A BADGE: drop the image in assetsBuild/badgesSrc/, add a row to the
  CSV, commit. Nothing else. ADDING A PAGE TO THE WALL: paste the two marker
  comments into it; the builder finds pages by scanning for the start marker,
  so it holds no list of pages.

  DO NOT HAND-EDIT the <ul class="badges"> block in the HTML, or anything in
  rootdomain/personal/badges/. Both are generated on every commit and your edit
  goes away without a word. The block is fenced by

    <!-- badges:start GENERATED by assetsBuild/badgeBuild.pl ... -->
    <!-- badges:end -->

  and the <ul> itself sits outside the fence, so a page can still carry its own
  classes on it.

  WHY THE MARKUP IS GENERATED and not just the images: each badge is re-encoded
  to lossless WebP and kept ONLY IF SMALLER, so the served extension is not
  knowable until the encoder has run. The wall serves 88x31.webp and nginx.png
  side by side. Hand-written src= attributes would have to be re-audited across
  eight pages every time a source image changed; they would rot into 404s
  instead. 15643 -> 9144 bytes, 42% off, nine badges of ten winning.

  nginx.png LOSES BY 4 BYTES and is served as PNG. That is the system working,
  not a bug — do not "fix" it by forcing WebP everywhere. zero-javascript.png
  wins by the same tiny margin the other way. At 88x31 the answer is per-image
  and cannot be guessed, which is the entire reason the script compares.

  GOTCHAS
    - cwebp CANNOT READ GIF, at any frame count — it fails with "Cannot read
      input picture file", which reads like a missing file. GIFs go through
      gif2webp. trans-flag.gif is 8 animated frames and survives as an animated
      WebP; verified frame-by-frame against the GIF at zero pixel difference.
    - Lossless always. These are pixel art with hard edges and tiny palettes:
      the case lossy WebP is worst at. Do not try -q 80.
    - The manifest is COMMITTED so a fresh clone is already warm. Mtimes play
      no part in the cache, because git does not preserve them.
    - webBadges.csv is RFC 4180: CRLF line endings, no comment syntax (which is
      why all of this is documented here and in the script instead of in it).
      .gitattributes carries `text eol=crlf` so a checkout re-establishes the
      line endings whatever the editor did.
    - badgeBuild.pl reads and writes EVERYTHING AS BYTES, deliberately. The alt
      text contains an emoji; decoding it would make the page a character
      string, and Perl would then re-encode the page's existing UTF-8 as
      Latin-1 — turning every curly quote in the file into mojibake, far from
      anything the script meant to touch. It announces itself only as "Wide
      character in print". There is a guard in the page writer that refuses to
      write a page that has gone wide.

  THE PANGRAM BADGE IS NOT PART OF THIS. personal/pangramHumanBadge.webp sits
  in five post <h1>s with a different link per page, so it is hand-written
  markup and outside the CSV. It was re-encoded once by hand (2723 -> 1482 B,
  lossless) and renamed at the same time: it used to be "my shitty Pangram 100%
  Human badge.png", addressed as my%20shitty%20Pangram%20100%25%20Human%20-
  badge.png. If it ever needs re-encoding, do it by hand again.
